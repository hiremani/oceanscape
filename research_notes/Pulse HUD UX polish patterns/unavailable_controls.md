# Presenting Unavailable, Disabled, Read-Only, and Not-Supported Controls

> Scope note for the report writer: the Pulse HUD has a **grey-not-hide** rule plus an always-show-a-reason rule. All findings below are framed to work *within* that rule — i.e., how to make shown-but-greyed controls calm, understandable, and discoverable — not how to hide them. Where a source recommends hiding, that is noted as a tension with the project rule, not an endorsement.

## Q1. Disabled vs. hidden vs. greyed vs. read-only: when does each win, and what are the usability/accessibility problems?

### Takeaway
The evidence strongly separates two cases the Pulse HUD currently blurs: **read-only** (a real value the user should read but cannot change — stays reachable, readable, contrast-compliant) vs. **disabled** (an action temporarily unavailable pending user action — often fails contrast and is skipped by assistive tech). The dominant usability failure of greyed/disabled controls is that they are a "communication dead end": users cannot tell *why* they are off or *whether/how* to enable them. Hiding is cleaner for things a user can *never* reach, but it destroys discoverability — which is exactly why the grey-not-hide rule is defensible for read-only and conditional controls.

### Cited Findings
- Carbon splits the two sharply: use **read-only** only for components that *could* be modified when enabled, when a process temporarily blocks edits, a lock limits concurrent editors, or permissions allow viewing but not editing; use **disabled** when a component is temporarily unavailable until the user acts (finishing a form, choosing an option). Do not convert disabled to read-only or vice versa. — [Carbon Design System — Read-only states pattern](https://carbondesignsystem.com/patterns/read-only-states-pattern/)
- Carbon: **read-only text color must still meet 4.5:1 contrast**, stays in the tab order, and is read by screen readers; **disabled content is skipped by screen readers and does not pass visual contrast**, so "use read-only whenever users need to read the information." — [Carbon Design System — Read-only states pattern](https://carbondesignsystem.com/patterns/read-only-states-pattern/)
- Cloudscape: use **disabled** when interacting could cause errors because a prerequisite is unmet (e.g., a delete button with nothing selected); use **read-only** when users must see a value but not change it (e.g., a field they lack permission to edit but that is still submitted); use **plain text** instead of a read-only control when *all* content is in a review state. — [Cloudscape — Disabled and read-only states](https://cloudscape.design/patterns/general/disabled-and-read-only-states/)
- NN/g's documented position: disabled buttons "appear clickable but provide no response or feedback," which confuses users; use them sparingly, make them accessible, and explain why they are disabled. — [NN/g — Why Disabled Buttons Hurt UX](https://www.nngroup.com/videos/why-disabled-buttons-hurt-ux-and-how-to-fix-them/)
- Concrete failure modes of disabled/greyed controls: users don't know why they're blocked ("we are blocked, but we don't know why"); keyboard and screen-reader users are shut out because disabled controls are typically not focusable; greyed styling has poor contrast (hard for low vision); and on a late-disabled control users can't tell whether it was off from the start or caused by their input. — [Smashing Magazine — Usability Pitfalls of Disabled Buttons](https://smashingmagazine.com/2021/08/frustrating-design-patterns-disabled-buttons/)
- Nielsen: a disabled control alone is a "communication dead end"; show inactive features as disabled in a muted color, explain *why*, and offer a path to enable — but **hide** features the user can *never* access (permissions, paid tier). He cites Microsoft's adaptive Office menus (items disappearing) as a case where hiding frustrated users, supporting that visible-disabled aids discoverability. He is explicit this is "based on the balance of arguments and limited evidence, not strong test data." — [UX Tigers (Jakob Nielsen) — Inactive Buttons](https://www.uxtigers.com/post/inactive-buttons)
- Automotive precedent for the grey-not-hide convention while moving: Volvo — "a grayed-out menu text cannot currently be selected" (feature not installed, or source not connected/empty); Honda — "certain manual functions are disabled or inoperable while the vehicle is in motion, and a grayed-out option cannot be selected until the vehicle is stopped"; Suzuki — unavailable screen buttons are dimmed. — [Volvo S80 support](https://www.volvocars.com/en-ca/support/car/s80/14w20/article/48225cf35a709c85c0a801516d9bf1e2); Honda and Suzuki owner manuals (via [search index](https://techinfo.honda.com/rjanisis/pubs/OM/AH/A30B2424IOM/enu/details/131245047-366428.html))

### Inferences
- The Pulse HUD's three categories map cleanly onto the literature: "read-only (shows the car's value)" = **read-only** (keep readable + contrast-compliant + reachable, NOT greyed-to-illegible); "not available / head unit overwrites" = **disabled** with a reason; "mockup" = also disabled-with-reason but the reason is honestly "not built yet / preview."
- The grey-not-hide rule is well-supported for read-only and conditionally-available controls (discoverability wins). It conflicts with Nielsen only for the narrow "never, by anyone" case — which barely exists here, since almost every greyed Pulse row is conditionally available (parked-only, trial-gated, source-dependent). So the rule is sound; the fix is reasons + de-emphasis, not hiding.

### Gaps
- No controlled A/B study quantifying grey-vs-hide for in-vehicle controls specifically; the automotive sources are manuals/convention, not usability tests. No single binding regulatory rule found on greyed functions (would need NHTSA/UNECE/Austroads/UMTRI primary docs).

## Q2. Making the REASON discoverable without permanent clutter

### Takeaway
Pair a **short, always-visible hint** with a **fuller on-demand explanation** (tooltip on hover / popover on tap / a longer message if the control is activated). Match reason length to the surface: tooltips for short in-context reasons, inline text or an alert for long/complex ones. Use templated reason wording so every greyed row explains itself in one consistent sentence.

### Cited Findings
- Cloudscape reason-surfacing rules: use a **tooltip** for short in-context reasons on buttons, select/multiselect items, tabs, segmented-control items, and calendar dates; use a **text description or alert** for long or complex reasons; **never put interactive content inside a disabled reason.** Wording = one sentence saying what is disabled and why, plus an optional second sentence on next steps. Templates: Permissions — "This action is available in/for [constraint]."; Prerequisites — "This action is available when [future action]."; Technical limits — "This action is unavailable due to [technical constraints]." — [Cloudscape — Disabled and read-only states](https://cloudscape.design/patterns/general/disabled-and-read-only-states/)
- Nielsen's two-layer pattern: pair a **short visible hint** with a **fuller explanation** — e.g., "Select an item to delete," "Save disabled: No changes made." Show the fuller explanation on hover (tooltip) or on tap (popover for touch); if the user activates the disabled control, show a longer message optionally linking to help; make the path to enabling easy to infer. — [UX Tigers (Jakob Nielsen) — Inactive Buttons](https://www.uxtigers.com/post/inactive-buttons)
- Smashing's discoverability fixes: if you must disable, keep it focusable with `aria-disabled` (not `disabled`), pair it with a **visible hint or tooltip** explaining what's missing, change the cursor to `not-allowed`, and announce changes via ARIA live regions; provide an explicit "way out" (e.g., a "Can't proceed?" affordance). — [Smashing Magazine — Usability Pitfalls of Disabled Buttons](https://smashingmagazine.com/2021/08/frustrating-design-patterns-disabled-buttons/)
- A third-party design system (Galaxus/Digitec, not Atlassian) states tooltips on disabled elements should give the reason the element can't be used and suggest the next step — consistent with the above, but note the Mozilla bug asking disabled toolbar buttons to explain themselves was closed WONTFIX, so native-widget support is uneven. — [Galaxus design system — Tooltip](https://galaxus.ch/designsystem/components/tooltip-design); [Mozilla bug 245264](https://www.bugzilla.mozilla.org/show_bug.cgi?id=245264)

### Inferences
- For a touch-only car screen there is no hover, so the "short visible hint + tap-to-expand" model fits best: the Pulse project's existing `off` reason string in `carcatalog.js` should render as the always-visible short hint; a tap (or info affordance) on a greyed row reveals the fuller reason/next step. This satisfies "always show a reason" while keeping the always-visible text to one short line (anti-clutter).
- Templated reasons map directly to the HUD's categories: parked-only → "Available when parked."; head-unit-overwrites → "Unavailable — the head unit controls this."; no CAN message → "Unavailable on this car."; mockup → "Preview — not yet connected." Consistent templates reduce perceived clutter because the eye learns one shape.

### Gaps
- No source gives tested guidance on tap-to-reveal reasons specifically on automotive center screens (glanceability / driver-distraction constraints on reading a tooltip while moving). The project's own parked-only gating partly moots this.

## Q3. Visually distinguishing read-only / informational vs. disabled / blocked vs. temporarily-unavailable

### Takeaway
Keep **read-only looking almost like enabled** (full-contrast text, normal layout, only the edit affordance removed) so users trust it as live data; make **disabled visibly muted/lower-contrast** so it clearly can't be acted on. The strongest single differentiator is contrast: read-only keeps 4.5:1; disabled is allowed to drop below. Cursor and icon tokens reinforce the split.

### Cited Findings
- Carbon read-only visual spec: **text color stays the same as enabled** and must meet 4.5:1; keep enabled layout and spacing; switch only *signifier* icons (chevron/close/calendar) to a disabled token while keeping context icons; borders may de-emphasize clickability; show an **arrow cursor** (not interactive) rather than a disabled cursor. — [Carbon Design System — Read-only states pattern](https://carbondesignsystem.com/patterns/read-only-states-pattern/)
- "Read-only should look close to enabled": keep labels and contrast intact, remove only editing (Material read-only field argument). — [Design Systems Collective — Read-Only Text Fields in Material Design](https://www.designsystemscollective.com/the-missing-state-in-most-design-systems-read-only-text-fields-in-material-design-6eb42fb45dd3)
- Disabled visual spec (NN/g): use **muted colors** — light gray, a desaturated color, or a subdued version of the enabled style — so it doesn't look clickable; the label may have **lower contrast than enabled but must stay legible**, and the contrast must not be high enough to imply it's clickable; disabled is usually lighter than enabled with lower label-to-background contrast; appearance must not change on interaction (no hover/pressed feedback). — [NN/g — Button States: Communicate Interaction](https://www.nngroup.com/articles/button-states-communicate-interaction/)
- Gray vs. muted-primary (Nielsen, observational): gray is instantly recognized as "disabled" by convention but can shout in a colorful UI; a muted version of the primary color stays recognizable and makes enabling feel like a subtle expected change; muted states often have low contrast (bad for low vision), so a higher-contrast faded color is a better compromise. One team's unpublished test found "users performed significantly better with the muted primary-color buttons," but Nielsen's own research found "no credible empirical evidence" isolating gray-vs-muted. — [UX Tigers (Jakob Nielsen) — Inactive Buttons](https://www.uxtigers.com/post/inactive-buttons)

### Inferences
- A three-way visual language for the HUD: (1) **Read-only / informational** — full-contrast value text, normal row, no toggle/affordance, small "info" styling; reads as a live readout. (2) **Disabled / blocked** — muted (ideally a desaturated version of the control's own accent, not flat gray), lower-contrast label but still legible, static on tap, `not-allowed`/arrow cursor, with the reason hint. (3) **Temporarily unavailable** (parked-only, source-disconnected, head-unit-overwritten) — same muted base as disabled but distinguished by the reason wording and ideally a state glyph (e.g., lock for parked-only, so the user learns it will become available), since the user's mental model differs (will-return vs. can't-here).
- The single most important rule for the HUD: do NOT grey read-only values to the same faint tone as blocked controls — that is the current clutter/confusion source. Read-only values are data the driver wants to read; keep them legible.

### Gaps
- No source prescribes exact token values or a standardized three-way visual scheme; design systems define two states (disabled, read-only), and "temporarily unavailable" is conveyed by wording rather than a distinct visual tier. The HUD will have to invent the third tier's visual cue (lock glyph is a reasonable, convention-aligned choice but untested here).

## Q4. Reducing visual load when many rows are non-actionable (grouping, de-emphasis, progressive disclosure, toggles)

### Takeaway
Within grey-not-hide, calm a cluttered screen by (a) **grouping** non-actionable rows, (b) **de-emphasizing** them (muted but legible), and (c) **progressive disclosure** — keep primary/actionable controls in view by default and defer secondary/unavailable ones to a subsidiary surface or a "show unavailable" toggle. Progressive disclosure is a deferral, not a hide, so it is compatible with the rule as long as the deferred rows remain reachable and their reasons discoverable.

### Cited Findings
- Progressive disclosure (NN/g): defer **secondary options to a subsidiary screen** so the primary options are the only ones shown by default, focusing attention; the canonical example is an "advanced settings" link, since most people never need those settings. Caveat: misapplied, it hides critical info — anything essential must stay visible. — [NN/g — Progressive Disclosure (video summary)](https://www.nngroup.com/videos/progressive-disclosure/)
- Cloudscape's one explicit clutter rule: **hide disabled items that are redundant AND that users can't enable** — i.e., only hide the truly dead ones; everything conditionally-enableable stays. (Tension to flag: the Pulse rule forbids hiding; the reconcile is to *defer/collapse* rather than remove, and to keep "can't enable by anyone" rows out only if the project ever relaxes the rule.) — [Cloudscape — Disabled and read-only states](https://cloudscape.design/patterns/general/disabled-and-read-only-states/)
- Replace blunt disabling with informative states where possible: show stock counts, mark an option "unavailable" instead of hiding, offer "Notify me"; use sensible defaults so the primary action is always available. — [Smashing Magazine — Usability Pitfalls of Disabled Buttons](https://smashingmagazine.com/2021/08/frustrating-design-patterns-disabled-buttons/)
- Nielsen reiterates the hide-vs-show line as the deciding factor for clutter: show as disabled when the user *could* enable it (discoverability); hide only when they never can. — [UX Tigers (Jakob Nielsen) — Inactive Buttons](https://www.uxtigers.com/post/inactive-buttons)

### Inferences
- Recommended layering for the HUD car-controls screens, all within grey-not-hide:
  1. **Group by actionability**, not just by function — actionable controls first/top; a labeled "Not available now" or "Read-only" group below, or a collapsible section. Grouping lets the eye skip the whole block instead of reading each greyed row.
  2. **De-emphasize the group** (muted header, tighter/denser rows, lower-contrast chrome) while keeping each row's value legible if it's read-only.
  3. **Progressive disclosure / "Show unavailable" toggle**: collapse the unavailable group by default with a count ("8 unavailable"), expandable on demand. This is deferral, not hiding — rows stay reachable and reasons stay discoverable, so it honors the rule. Trade-off: a collapsed group hides the reasons until expanded, so the collapsed header itself should carry the dominant reason when the whole group shares one (e.g., "Available when parked (8)").
  4. **Parked-only grouping is especially valuable**: when the car is moving, the large block of parked-only controls can collapse to a single "Available when parked" summary row, dramatically cutting clutter exactly when glance-time is scarcest, then expand when parked.
- A "mockup" row is the weakest case for permanent visibility; if the project wants less clutter without breaking the rule, mockups can live behind the progressive-disclosure toggle labeled "Preview" rather than interleaved with real controls.

### Gaps
- Dates in the progressive-disclosure origin story conflict across sources (1983 / 1995 / 2006) — not material to the guidance, but don't cite a specific year. No quantitative study found on collapse-by-default vs. show-all for in-car settings density specifically.

## Q5. Accessibility: contrast, screen-reader semantics, focusability (disabled vs read-only)

### Takeaway
Use **native `readonly`/`disabled` on real form controls**, and `aria-readonly`/`aria-disabled` only on custom widgets. The critical accessibility distinction: **read-only stays focusable, readable, and contrast-compliant; `disabled` (native) is removed from the tab order and is exempt from contrast** so screen readers and low-vision users lose it. For any value a user needs to *read*, prefer read-only (or `aria-disabled`, which stays focusable) over native `disabled`.

### Cited Findings
- `aria-readonly="true"` "indicates that the element is not editable, but is otherwise operable"; it stays focusable and the value is copyable/selectable and (for native controls) submitted. If you set the native `readonly` attribute you don't need `aria-readonly`. — [MDN — aria-readonly](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Attributes/aria-readonly)
- `aria-disabled="true"` exposes the element as disabled but keeps it in the accessibility tree and **does not block interaction by itself** — the author must enforce the no-op in JS; it keeps the element focusable (unlike native `disabled`). Native `disabled` is skipped by Tab, fires no click/focus events, and is not submitted. — [MDN — aria-readonly](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Attributes/aria-readonly) (aria-disabled/native rows from ARIA/HTML spec, noted as such on the page)
- Screen-reader/contrast split (Carbon): read-only is navigable but not operable, stays in tab order, is read by screen readers, and its text meets contrast; disabled cannot be reached by keyboard, is skipped by screen readers, and fails contrast. — [Carbon Design System — Read-only states pattern](https://carbondesignsystem.com/patterns/read-only-states-pattern/)
- Expose disabled state via `aria-disabled="true"` to keep the button in the tab order while telling screen readers it's inactive (NN/g). — [NN/g — Button States: Communicate Interaction](https://www.nngroup.com/articles/button-states-communicate-interaction/)
- Don't set `aria-readonly="true"` and `aria-disabled="true"` together — pick based on whether the value is valid-but-locked (readonly) or should be ignored for now (disabled). Disabled controls are generally treated as exempt from the WCAG 1.4.11 non-text-contrast requirement, though a clear visual cue is still good practice; disabling a submit button with no explanation is argued to risk SC 3.3.1. These come from secondary guides/forum/W3C discussion, so verify against the current ARIA spec/WCAG understanding docs. — [DHiWise — aria-disabled vs disabled](https://dhiwise.com/post/aria-disabled-vs-disabled); [W3C public-pfwg list](https://lists.w3.org/Archives/Public/public-pfwg/2014Sep/0108.html)

### Inferences
- For the Pulse HUD WebView: render read-only car values as readable, full-contrast, focusable text (not a greyed/`disabled` control), so a future accessibility pass (TalkBack / large-text) exposes them. For controls that are blocked (parked-only, head-unit-overwritten, mockup), prefer `aria-disabled="true"` + enforced no-op + visible reason over native `disabled`, because `aria-disabled` keeps the control focusable so its reason can be reached — directly supporting the "always show a reason" rule for assistive tech, not just sighted users.
- Because WCAG exempts native-disabled from contrast, the current "greyed to near-illegible" rows are technically permissible but hostile; moving read-only to full contrast and disabled to muted-but-legible fixes the real-world readability problem the HUD has, regardless of the exemption.

### Gaps
- Exact screen-reader announcement wording for aria-disabled vs aria-readonly varies by SR/version (MDN says so); no automotive-specific accessibility standard found. WCAG attribute-choice claims rest on secondary sources; primary ARIA spec / WCAG understanding docs were not fetched directly in this pass.
